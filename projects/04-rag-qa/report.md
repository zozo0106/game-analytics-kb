# 知识库 RAG 问答 · 完整报告

> 项目编号 `PRJ-04`｜分析日期 2026-09-16｜语料：本仓库 `docs/`（10 篇 · 72 块）
> 流程：`build_index.py` → `ask.py` / `eval_retrieval.py` / `ablation_heading.py`

---

## 0. 摘要（TL;DR）

**结论：给知识库接上一个可评测的检索问答层，全程零 API key、离线可复现。**

- 混合检索（BM25 + LSA + RRF）在 **42 题标注**集上 **Recall@1 = 0.786、Recall@5 = 0.976、MRR = 0.855**
- 域外问题拦截 **5/5**、域内可答题作答率 **42/42**
- 消融实验：**把标题路径加进检索文本**，混合 R@1 **+9.5pp**（0.691 → 0.786）、MRR **+6.7pp**
- 反直觉发现：**语料只有 72 块时，BM25 的 R@1（0.738）不低于稠密检索（0.691）**；稠密的价值在语义泛化

> ⚠️ 语料为本仓库自有知识库文档；评测集为人工标注（仓库内 `data/eval_questions.json`）。无真实业务数据。

---

## 1. 背景与目标

知识库（本仓库 `docs/`）写完后遇到的问题是**"没人翻"**：口径散落在 10 篇文档里，记不住也搜不准。

直接问 LLM 不行 —— **LLM 不知道库里的口径**，硬答就是编造。RAG 的思路是：**先检索证据，再基于证据作答**。

本项目要证明三件事：
1. 能在**不依赖任何云服务/API key** 的前提下把 RAG 跑起来（离线可复现）
2. 能把**检索层质量量化**（而不是"感觉还行"）
3. 能让系统在**答不了时拒答**，而不是硬凑一段看似相关的答案

## 2. 方法

### 2.1 分块（chunking）

按 Markdown 二级标题（`##`）切块，保留"文档标题 › 章节标题"路径；剔除 frontmatter、`延伸阅读`、`参考来源`（纯链接，是检索噪声）。
结果：10 篇文档 → **72 块**。

**关键设计：检索文本 = 标题路径 + 正文**，但展示/抽取仍用干净正文。
中文知识库的标题信息密度极高（如"留存体系：D1/D7/D30、Cohort 与留存曲线形态解读"），加进索引几乎零成本（见 §4.1 消融）。

### 2.2 分词（tokenization）

不引入 jieba：**中文按「单字 + 双字 bigram」切，英文/数字按词切**。
bigram 天然覆盖了大部分中文词（"留存"→ 留、存、留存），在检索场景效果足够，且**免词典依赖**。词表规模 8,122 token。

### 2.3 稀疏检索：BM25

标准 BM25（k1=1.5，b=0.75），IDF 用带平滑的常用变体：

```
score(q,d) = Σ_t IDF(t) · f(t,d)(k1+1) / [ f(t,d) + k1(1 − b + b·|d|/avgdl) ]
```

BM25 的 `b` 参数做长度归一化——注意这也是**短块容易被高估**的原因（见 §6 局限）。

### 2.4 稠密检索：LSA

TF-IDF → `TruncatedSVD`（71 维）→ L2 归一化 → 余弦相似。
选择 LSA 而非 sentence-transformers，是为了**离线可复现**；它是"离线版 embedding"，接口与真向量模型一致。

### 2.5 融合：RRF（倒数排名融合）

```
score(d) = Σ_r 1 / (k + rank_r(d))     # k=60
```

RRF 只利用**排名**，因此对"BM25 分数 vs 余弦相似度量纲不同"的问题天然免疫，免去加权调参。

### 2.6 作答与拒答

- **抽取式作答**：从 top-3 分块里挑句子，得分 = 命中 token 的 IDF 之和 ÷ √句长；只保留 ≥ 最佳分 55% 的句子（防填充句），最多 3 句，按原文顺序输出 + 标注来源
- **拒答闸门**（阈值经标注集标定）：
  - 未登录词占比 > **33%** → 域外问题
  - top-3 最高覆盖率 < **15%** → 知识库未覆盖

## 3. 评测设计

- **评测集**：42 题域内（人工标注 gold 文档）+ 5 题域外（期望拒答）= **47 题**；源文件入库
- **指标**：Recall@1/3/5（top-k 命中 gold 文档）、MRR；域外看拦截率，域内看作答率
- **对比**：BM25 / LSA / Hybrid 三模式；另做「标题路径」消融（`ablation_heading.py`）

## 4. 结果

| 检索模式 | Recall@1 | Recall@3 | Recall@5 | MRR |
|:---|:---:|:---:|:---:|:---:|
| BM25（稀疏） | 0.738 | 0.929 | 0.976 | 0.836 |
| LSA（稠密） | 0.691 | 0.976 | 0.976 | 0.818 |
| **混合（RRF）** | **0.786** | 0.905 | 0.976 | **0.855** |

**拒答**：域外 5/5（100%）拦截；域内 42/42（100%）作答。

值得注意的两个细节（不做粉饰）：
- **混合在 R@3 上反而略低于单路**（0.905 vs BM25 0.929）：RRF 融合偶尔把某题的 gold 从 top-3 挤到第 4 位，但 R@1 / MRR 更优，整体是赚的
- **除 R@5 外都未饱和**：42 题里有 **9 题**的 gold 不在 rank 1 —— 说明区分度真实存在，不是"题目太简单"

### 4.1 消融：标题路径入索引

同一语料、同一评测集，只改「检索文本加不加标题路径」一件事（`data/ablation_heading.json`）：

| 索引文本 | 模式 | R@1 | R@3 | MRR |
|:---|:---|:---:|:---:|:---:|
| 仅正文 | BM25 | 0.643 | 0.929 | 0.767 |
| 仅正文 | LSA | 0.500 | 0.857 | 0.677 |
| 仅正文 | 混合 | 0.691 | 0.905 | 0.788 |
| **正文 + 标题路径** | BM25 | **0.738** | 0.929 | **0.836** |
| **正文 + 标题路径** | LSA | **0.691** | 0.976 | **0.818** |
| **正文 + 标题路径** | **混合** | **0.786** | 0.905 | **0.855** |

增量（加标题 − 仅正文）：

| 模式 | ΔR@1 | ΔMRR |
|:---|:---:|:---:|
| BM25 | +9.5pp | +6.9pp |
| LSA | **+19.1pp** | **+14.0pp** |
| 混合 | +9.5pp | +6.7pp |

**解读**：中文短查询（"留存曲线尾部平台期代表什么"）里，最关键的词往往就是章节标题里的词；标题不入索引，等于把这些锚点丢了。稠密检索受益最大（+19.1pp）——因为 LSA 本来最缺乏精确词面匹配，标题提供的正是它缺的"强锚点"。

### 4.2 发现：小语料上稠密检索不一定赢

BM25 R@1 = 0.738 > LSA R@1 = 0.691。原因：
- 语料只有 72 块，**词表重叠度高**（同一主题的术语在文档间反复出现），稀疏匹配已经很强
- LSA 71 维是对整个 TF-IDF 矩阵的低秩近似，**信息有损**；语料小、维度低时损失更明显
- 稠密的相对优势在**语义泛化**（同义改写、"ROAS 回收"↔"回本周期"），本项目评测集里这类改写题占比不高
- 但稠密的 **R@3 更高**（0.976 vs 0.929）—— 它更擅长"把对的捞进候选"，只是排序头部不如 BM25 精准

**工程含义**：别一上来就上向量库。先建 BM25 基线 + 评测集，用数据说话。

## 5. 拒答：为什么这是 RAG 的必答题

不做拒答的 RAG 是**危险的**：用户问"今天晚饭吃什么"，它也能从知识库里凑出一段看着相关的话。这不是能力，是事故。

实测（47 题标注集）：域外问题拦截 5/5、域内可答题作答率 42/42。
阈值标定依据：域内问题未登录词占比 **≤ 0.29**、域外 **≥ 0.38** → 取 0.33 作为分界；覆盖率闸门（0.15）兜住"词都认识但组合起来无人回答"的情况。

阈值是**经验值**，换语料必须重新标定——所以评测脚本会把误拒/漏拒直接打印出来，而不是只给一个好看的汇总数。

## 6. 诚实的失败案例与局限

**失败案例 1：进了 top-5 ≠ 答得对**
问"LTV 应该按什么口径计算"，gold 文档 **在 rank 3**（检索算命中），但 **top-1 是另一篇**——"口径"这个泛化词命中了 `churn-analysis.md` 的标题"定义流失（口径先行）"。抽取式作答只看 top-3，于是**答错**。
→ 说明**检索指标和答案质量是两回事**；本项目只自动评检索，答案质量未自动评（见局限）。

**失败案例 2：评测集口径会"冤枉"检索**
问"SRM 是什么"，gold 标为 `pitfalls.md`，但 `ab-test-design.md` 里同样讲了 SRM 且被排到 top-1 → 被判"漏检"。这是**单 gold 标注在多文档重复概念上的固有缺陷**，不是检索坏了。

**失败案例 3：加文档会挤动邻居**
本项目写这篇报告期间新增了一篇文档（`06-ai-playbook/rag-setup.md`），语料从 9 篇 66 块变成 10 篇 72 块 —— 几道题的 top-1 因此换人（如"sBG 和 Pareto/NBD 模型是做什么的"的 top-1 被新文档抢走）。**语料是活的，文档一多就要重跑评测**，别拿半年前的指标当现状。

**局限（如实标注）**
1. **答案质量无自动评测**：无 gold 答案，抽取式答案只能人工抽查；上生成式后需要 LLM-as-judge 或人工评审
2. **评测集小（47 题）且由作者本人标注**，存在主观偏差；指标置信区间未计算
3. **LSA 不是真语义向量**：同义改写类问题会被低估，稠密模式的结论不能直接外推到 sentence-transformers
4. **短块易被 BM25 高估**：最短板仅 57 字符（"概述"），长度归一化会抬高它们；更大语料下应先合并过短块
5. **语料小**（72 块），所有结论都在"小语料"前提下成立，上生产（万级块）需重跑评测

## 7. 结论

1. **RAG 的瓶颈在检索**：本项目把评测做在检索层，得到了可复现的基线（混合 R@1 0.786 / R@5 0.976 / MRR 0.855）
2. **标题路径入索引 = 最高性价比改动**（混合 R@1 +9.5pp、LSA +19.1pp），任何中文知识库都值得先做这一条
3. **小语料先上 BM25**，用评测集证明稠密检索的增益再引入向量库
4. **拒答是必答题**：域外 100% 拦截、域内 100% 作答，说明阈值标定可控
5. **下一步**：换 sentence-transformers 真向量对比 → 加答案级评测（LLM-as-judge + 人工抽检）→ 语料上量后换 FAISS/Elasticsearch
