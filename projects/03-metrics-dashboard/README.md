# 03 · 指标体系看板

> 一句话：把"散落的指标"变成**一套能自解释、能告警、能自助下钻的指标体系** —— 北极星到诊断指标的分层设计 + SQL 指标层 + 自包含静态看板。
> 技术栈：SQL（指标层）+ Python（周期对比 / 异常检测 / 看板渲染）｜数据：合成（可一键复现）

---

## 业务问题

分析师最常被甩来的一句话是："帮我搭个看板。"

难的不是画图，是**三件更底层的事**：
1. **指标怎么分层？** 一个北极星（North Star）+ 一级指标 + 诊断指标 + 护栏指标，各有各的位置，不能一锅乱炖
2. **口径怎么统一？** 同名不同义（ARPU 分母是 DAU 还是付费用户？）是数据团队最大的事故来源
3. **指标怎么自解释？** 涨了是节日还是版本？跌了要不要报警？——需要**自动化异常检测**，而不是等人肉盯盘

本项目用一款 F2P 手游 180 天的合成经营数据，把上面三件事各落地一遍，产出一个**双击即开的静态看板**。

## 指标体系设计（本项目的骨架）

| 层级 | 指标 | 作用 |
|:---|:---|:---|
| **北极星** | DAU（日活跃用户） | 全公司对齐的唯一目标；其余指标都解释它 |
| **一级（四大盘）** | 新增 DNU · 留存 D1/D7/D30 · 参与（人均时长/会话）· 变现（ARPU/付费率） | 回答"增长从哪来、留得住吗、玩得深吗、赚得到吗" |
| **诊断（下钻）** | 分渠道 / 机型 / 地域的 DAU、ARPU、付费率 | 定位是"哪个渠道/哪个人群"出了问题 |
| **护栏** | 留存、人均时长、付费率 | 只允许不劣化；防止"为了流水把体验做坏" |

> 分层框架参考 HEART 用户体验度量框架（Rodden et al. 2010），并结合游戏业务调整为"规模-留存-参与-变现"四大盘。

## 方法（三段式）

```
明细事实表(5,760 行: 180天 × 渠道 × 机型 × 地域)
   │  sql/daily_kpi.sql      ← 聚合 + 窗口函数(LAG 环比 / 7日移动均线) + 留存关联
   ▼
日级 KPI 宽表(metrics_daily.csv, 20 列)
   │  python/01_kpi_overview.py   ← ① 周期对比(WoW)  ② 异常检测(去季节 + 稳健 z)
   ▼
   │  python/02_dashboard.py      ← 渲染自包含 HTML 看板 + 渠道图
   ▼
静态看板(assets/dashboard.html) + 告警清单(alerts.json)
```

**异常检测口径**：先按"同一星期几的滚动中位数"**去掉周内季节性**，再算**改进 z 分数**（0.6745×(x−中位数)/MAD，见 Iglewicz & Hoaglin 1993），|z|>3.5 告警。用中位数/MAD 而非均值/标准差，是因为流水这类重尾指标会被大 R 和活动脉冲带偏。

## 结果（合成数据，seed=42 可复现）

**最近 7 天 vs 前 7 天（周环比）**

| 指标 | 前 7 天 | 最近 7 天 | 环比 |
|:---|:---:|:---:|:---:|
| DAU | 144,038 | 143,874 | −0.11% |
| 流水 | 236,354 | 235,666 | −0.29% |
| ARPU | 1.64 | 1.64 | −0.16% |
| 付费率 | 2.57% | 2.56% | −0.53% |
| 人均时长 | 45.05 min | 44.99 min | −0.15% |
| D1 留存 | 45.71% | 46.10% | **+0.85%** |

**渠道拆解（最近 30 天均值）**

| 渠道 | DAU | 占比 | ARPU | 付费率 |
|:---|:---:|:---:|:---:|:---:|
| 自然量 | 48,613 | 34.0% | 1.21 | 1.88% |
| 买量-信息流 | 37,133 | 26.0% | 1.96 | 3.06% |
| 应用商店 | 37,038 | 25.9% | 1.63 | 2.53% |
| 买量-KOL | 20,049 | 14.0% | 2.19 | 3.41% |

> 洞察：买量用户的 ARPU/付费率显著高于自然量（KOL 最高），**但获客成本也高** —— 单看 ARPU 会误判渠道质量，必须结合 CAC 看 ROAS（本项目仅到指标层，未含成本数据）。

**异常检测：命中 28 个点，全部对上埋入剧情**

| 时段 | 命中 | 对应事件（自检用，正常流程不读日历） |
|:---|:---:|:---|
| 2026-04-28 ~ 05-03 | 18 点（dau/流水/付费率齐跌） | **版本 2.1 崩溃**（活跃 −12%、时长与流水同挫） |
| 2026-06-27 ~ 06-29 | 9 点（DAU +15~20σ、流水 +60%） | **限时充值活动**（付费率 2.6%→4.2%） |
| 2026-08-18 | 1 点（边缘，z=+3.6） | 噪声单点，阈值附近需人工确认 |

> 关键设计：**先去掉周末季节性**再检测，否则每个周末都会被误报为异常（未去季节时曾多出 3 个周末假阳性）。

## 看板

`assets/dashboard.html` 是**单文件、零依赖**的静态看板（内联 CSS/SVG，不引任何 CDN/前端框架），浏览器直接打开：

- 6 张 KPI 卡片（带 WoW 环比升降）
- DAU 趋势图（叠加 7 日均线，异常日红线竖带标注）
- 渠道拆解表 + 告警清单 + 最近 10 天明细

> 为什么不用 Streamlit/Superset？见下方"设计说明"——静态 HTML 的最大优势是**交付零成本**（发个文件就行），适合当作品集直接展示。

## 设计说明（面试常被问）

- **北极星为什么选 DAU 而不是流水？** 北极星要"全公司都能影响、且可持续"，流水太滞后且易被活动脉冲污染；DAU 是留存/参与/变现的公共上游，稳定且可拆解。
- **为什么指标要分"护栏"？** 单追北极星会走歪（例如为拉 DAU 猛推买量，结果留存崩了）。护栏指标给北极星装刹车。
- **异常检测为什么用中位数 + MAD？** 均值/标准差会被离群点（大 R、活动）自身拉偏，导致"异常把阈值撑大、反而测不出异常"。中位数/MAD 稳健。
- **为什么要先去星期季节性？** 游戏流量有强周内节律，不去季节的话每个周末都是"假警报"，告警会被噪声淹没。
- **为什么交付静态 HTML？** 零依赖、零部署、可离线、可版本管理；对"作品集展示"场景性价比最高。生产环境再换 BI 平台也不冲突（指标逻辑在 SQL 层已沉淀）。
- **下一步可做**：接入真实 BI（Superset）/ 指标血缘与口径版本管理 / 同比与预测性告警（Prophet 类）/ 漏斗与 Cohort 留存看板化。
