# NL2SQL 助手 · 分析报告

> 数据：合成游戏库（6,000 用户 / 150,519 行为行 / 6,133 笔订单 / GMV 506,194.00 元）
> 基准日 REF_DATE = 2026-06-30，所有「最近N天」= [REF-(N-1), REF]
> 全部数字由 `python/run_eval.py` 实测，可一键复现。

---

## 1. 业务问题

数据分析团队被「帮我拉个数」淹没。这类需求高度模板化：**指标 × 维度 × 时间窗 × TopN**。

如果能把这类查询自助化，分析师省下的时间可以投到真正的归因和策略上。
但企业里这类工具失败的原因通常不是"SQL 写不出来"，而是**写对了也没人敢用**：

- 口径错（"活跃"没定义）→ 数字对不上财务报表 → 一次就失去信任
- 不可验证（没评测集）→ 不知道什么时候会错
- 不安全（能生成 DROP）→ 不敢给业务直接连库

所以本项目的目标不是"做个人人都能问的 ChatBI"，而是：
**在可量化、可回滚、可审计的前提下，把 N 天 → 10 秒。**

---

## 2. 方法

| 阶段 | 做法 | 为什么这么做 |
|---|---|---|
| Schema Linking | 关键词表 + **最长匹配优先** | 修掉 `商品`/`商品类型` 的子串抢占 |
| 时间归一化 | 同义词 + 相对时间解析（最近N天/本月/上月/YYYY年M月/N月） | 口语里时间表达最散 |
| Query Planning | 指标字典 × 维度字典 × TopN | **口径收敛在字典里，不交给模型猜** |
| Rendering | 模板拼装 | 生成结果可审计、可 diff |
| 护栏 | 单语句 / 只读 / 禁危险函数 / 强制 LIMIT | 自然语言是不可信输入 |
| LLM 分支 | OpenAI 兼容适配 + 失败回退规则引擎 | 泛化交给模型，兜底留给工程 |

---

## 3. 评测设计（本项目最重要的一节）

沿用 Text-to-SQL 领域的 **Execution Accuracy (EX)**：不看 SQL 字符串像不像，
只看**在同一库上跑出来的结果集是否一致**（Yu et al., 2018）。理由很实际——同一件事有一百种写法。

三套集合，故意做成三种"自欺等级"：

| 集合 | 构造方式 | 用途 | 是否可信 |
|---|---|---|---|
| Dev（40 条） | 按规则能力边界手写 | 开发调试 | ❌ 同源，必然虚高 |
| Paraphrase（15 条） | 换成运营口语 | 测同义词缺口 | ⚠️ 调词表时看过了，已被污染 |
| **Held-out（20 条）** | 一次性写好，**只跑一次，不回头调** | 唯一成绩 | ✅ |

> 这一节才是简历上该讲的东西：**"我知道我的数字有多可信，以及为什么。"**

## 4. 结果

### 4.1 全局

| 集合 | n | 正确 | EX |
|---|---:|---:|---:|
| Dev | 40 | 40 | 100.0% |
| Paraphrase（归一化前） | 15 | 7 | **46.7%** |
| Paraphrase（归一化后） | 15 | 15 | 100.0%（已污染，不作数） |
| **Held-out** | **20** | **12** | **60.0%** |

![eval](../assets/eval_summary.png)

### 4.2 保留集分难度

| 难度 | n | EX | 说明 |
|---|---:|---:|---|
| easy | 5 | 80.0% | 单指标 + 时间窗 |
| medium | 9 | 88.9% | + 维度分组 |
| **hard** | **6** | **0.0%** | 比率 / 多指标 / 嵌套 / 隐式列 |

**easy+medium 合计 12/14 = 85.7%；hard 0/6。** 能力边界非常锋利。

### 4.3 失败清单（保留集 8 条，逐条归因）

| # | 问题 | 真实需求 | 引擎行为 | 失败类型 |
|---|---|---|---|---|
| H1 | 昨天的活跃用户数 | 相对日期"昨天" | 忽略时间窗 → 返回全量 DAU | 词表缺口 |
| H2 | 各渠道昨天带来多少收入 | 同上 + 维度 | 同上 | 词表缺口 |
| H6 | 收入最高的那一天是多少 | 需自行推断 "group by 日期" | 返回全局总收入 | 隐式列引用 |
| H7 | 各渠道的收入和订单数 | 双指标同查 | 只出收入 | 多指标 |
| H9 | 各商品类型的平均订单金额 | `AVG(amount)` | 落到"订单数" → `COUNT(*)` | 指标字典缺项 |
| H10 | 最近7天活跃用户里付费的有多少 | `IN (子查询)` 交集 | 只算付费用户 | 嵌套语义 |
| H14 | 各渠道人均会话数 | `SUM/COUNT(DISTINCT)` | 落到会话总量 | 复合指标 |
| H15 | 各商品类型收入占比 | 分母 = 全局 | 落到收入绝对值 | 比率 |

**8 条里 0 条是"SQL 语法写错"**，全是语义/口径层的问题。

## 5. 关键结论

### 结论 1：自测 100% 是危险信号，不是成绩

Dev 集 100% → 口语集 46.7%。落差 53pp 全部来自"题目是按规则能力边界写的"。
**任何 NL2SQL 报告，先问：题是谁出的？调参时看过没有？n 是多少？**
（n=20 时，60% 的 95% 置信区间约 [36%, 81%]，别当精确值用。）

### 结论 2：最便宜的提升不在模型上

口语集 8 条失败里，**8 条都是词表没覆盖**（玩家→用户、多少钱→收入、一周→7天、每一天→每天）。
约 20 行同义词归一化 → 46.7% 提到 100%。
**先穷尽词表和口径，再考虑换模型。** 这条在任何 NL2SQL 项目里都成立。

### 结论 3：规则引擎的天花板在"语言→口径映射"，不在 SQL

保留集 hard 0/6。加规则能救，但每条规则都是一次人工维护，且互相冲突风险上升
（这次就踩了 `商品` 抢占 `商品类型` 的坑，只能靠"最长匹配优先"这种通用策略兜）。
**比率 / 多指标 / 隐式列 / 指代** 这四类，天然属于大模型的泛化区。

所以正确的架构是混合，而不是二选一：

```
LLM 负责：理解意图、映射口径、处理口语变体
工程负责：Schema Card 精选、指标字典约束、执行自检、护栏、失败回退
```

### 结论 4：护栏必须是代码，不能是提示词

`sql_guard.py` 实测拦截 `DROP TABLE`、多语句注入、`--` 注释绕过、`load_extension()`。
但代码护栏挡不住所有情况，生产环境第一层永远是**只读数据库账号**——
这是权限问题，不是 NLP 问题。

## 6. 如果继续做（按 ROI 排序）

1. **把保留集扩到 200+ 条**，并按"单指标/比率/多指标/嵌套"分层统计 —— 现在的 20 条说服力不够。
2. **补口径字典**：ARPU/ARPPU/占比/人均 这类复合指标做成参数化模板（覆盖 H9/H14/H15）。
3. **接 LLM 跑同一套保留集**，出一张"规则 vs LLM vs LLM+规则"的对比表 —— 这是最有价值的一张图，但没有 API key 就不编数字。
4. **加澄清机制**：问题口径不清时反问（"你说的活跃是指登录还是有时长？"），比硬猜更专业。
5. **失败日志闭环**：把线上问错的句子自动进"待补词表"，一周一清。
