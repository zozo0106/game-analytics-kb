# 把知识库做成 RAG 问答：检索层才是瓶颈

> 一句话摘要：知识库写完的最大问题是"没人翻"。RAG（检索增强生成）能让文档"自己回答问题"，但**做得好不好，九成取决于检索层**。这篇讲清怎么建一个可评测、会拒答的 RAG 问答，并附本仓库实测数字。

> ✅ 核对状态：方法学已对照 RAG（Lewis et al. 2020, NeurIPS）、BM25（Robertson & Zaragoza 2009）、RRF（Cormack et al. 2009, SIGIR）、DPR（Karpukhin et al. 2020, EMNLP）、LSA（Deerwester et al. 1990）等权威源核对。案例数值来自本仓库 `projects/04-rag-qa/`，语料为自有文档，**非真实业务数据**，固定随机种子可复现。

## 背景

知识库（比如这套游戏数据分析文档）写多了会遇到一个尴尬：**自己的口径都记不住，更别说别人会去翻。**

直接把文档丢给 LLM 行不行？不行。**LLM 不知道你库里的口径**——你问"我们的 ARPU 分母是 DAU 还是付费用户"，它只能按通用理解编一个。企业场景里，**"不知道却硬答"比"不答"危险得多**。

RAG（Retrieval-Augmented Generation，检索增强生成）的思路很朴素：**先从知识库检索出相关段落，再让模型只基于这些段落作答**。检索是"事实的入口"，生成只是"把事实说人话"。

这里有个行业里最常见的误区：**大家把精力花在换更大的模型上，而 RAG 的效果瓶颈其实在检索层。** 检索没把对的段落捞出来，再强的模型也只能胡说。所以这篇文章把重点放在检索，并且**先建评测集**。

## 框架：RAG 的五步链路

| 步骤 | 做什么 | 游戏/业务类知识库的坑 |
|:---|:---|:---|
| 1 分块 | 长文切成可检索单元 | 切太碎丢上下文、切太整检索不准 |
| 2 分词 | 把中文/术语切成检索 token | 中文分词器依赖词典，"留存"这类词易被切坏 |
| 3 检索 | 稀疏 + 稠密两路召回 | 只用一种，召回有系统性盲区 |
| 4 融合 | 把两路结果合成一个排序 | 分数量纲不同，加权求和要反复调参 |
| 5 作答 | 基于证据组织答案 + **拒答** | 不拒答 = 用户问什么都能凑一段 |

## 方法：四个关键口径

**① 分块：按标题切，标题也入索引。**
按 Markdown 二级标题切块，保留"文档标题 › 章节标题"路径。**关键一步：把标题路径拼进检索文本**（展示时再剥掉）。中文知识库的标题信息密度极高（如"留存体系：D1/D7/D30、Cohort"），这是性价比最高的一行改动。

**② 分词：中文用「单字 + 双字 bigram」。**
"留存"被切成 留 / 存 / 留存，无需词典依赖；英文数字按词切。检索场景下效果足够，还免去了分词器这个依赖。

**③ 检索：BM25 + 稠密两路，RRF 融合。**
BM25 是稀疏检索的经典（按词命中 + IDF 加权 + 文档长度归一）；稠密用向量相似度补足语义泛化。"融合"用 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：只取排名、`Σ 1/(k+rank)`，天然免疫量纲差异，免调参。

**④ 拒答：低置信时明确说"不知道"。**
两道闸门：**未登录词占比过高**（问题里的词语料里从没见过）或**最高覆盖率过低**（词都认识但组合起来无人回答）→ 直接答"知识库中没有相关内容"。

## 案例（本仓库实测 · 合成/自有语料）

用本仓库 `docs/` 的知识库文档（10 篇切成 72 块）搭了一个零 API key、离线可复现的 RAG，人工标注 **42 道域内题 + 5 道域外题**做评测：

| 检索模式 | Recall@1 | Recall@3 | MRR |
|:---|:---:|:---:|:---:|
| BM25（稀疏） | 0.738 | 0.929 | 0.836 |
| LSA（稠密） | 0.691 | 0.976 | 0.818 |
| **混合（RRF）** | **0.786** | 0.905 | **0.855** |

域外问题拦截 **5/5**，域内可答题作答率 **42/42**。

几个反直觉的结论：

- **标题路径入索引 = 最大单项收益**：只改这一件事（同语料同评测集），混合 R@1 从 0.691 → 0.786（+9.5pp），稠密检索更是 +19.1pp。零成本，但很多实现都漏了。
- **小语料上 BM25 不输稠密检索**：只有 72 块时，BM25 的 R@1（0.738）高于向量（0.691）；向量只在 R@3 上更优（0.976 vs 0.929）。**别一上来就堆向量库**——先建 BM25 基线 + 评测集，用数据说话。
- **"进了 top-5" ≠ "答得对"**：有一题 gold 文档在 rank 3（检索算命中），但 top-1 被一个泛化词带偏，抽取式答案因此答错。**检索指标和答案质量是两件事**，都得评。
- 顺带一提，加入本文（语料从 9 篇变 10 篇）后有几道题的 top-1 换了人——**语料是活的，文档一多就要重跑评测**。

## 要点速记

- [ ] RAG 的瓶颈在**检索层**，不在模型：先建评测集（Recall@k / MRR），再谈优化
- [ ] 分块按标题切，**标题路径一定要入索引**（中文知识库收益最大，实测 +9.5pp R@1）
- [ ] 中文检索可用「单字 + bigram」免分词器；BM25 + 稠密两路，**RRF 融合免调参**
- [ ] **小语料先上 BM25**，别默认向量检索更强；稠密的价值在语义泛化，语料小体现不出来
- [ ] **拒答是必答题**：不拒答的 RAG 会为任何问题硬凑答案，企业场景里这是事故
- [ ] 检索指标 ≠ 答案质量：检索命中不代表答得对，答案级评测要单独做
